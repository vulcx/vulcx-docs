The Vulcx API rate limits by **cost**, not by request count, against a budget set by your plan.
Limits apply **per account**: every key you hold draws from the same budget.

## A budget, weighted by what you ask for

A quote is a read against in-memory pool state. A swap runs that same routing and then builds a
transaction, resolves its lookup tables, and simulates it. Charging both "one request" makes the
budget meaningless for whichever of the two you sized it against, so each request debits your
bucket by its weight:

| Endpoint | Cost |
|---|---|
| `GET /api/v1/quote` | 1 |
| `GET /api/v1/price`, `GET /api/v1/price/:mint` | 1 |
| `GET /api/v1/pools/*` | 3 |
| `POST /api/v1/cpi/route-accounts` | 3 |
| `POST /api/v1/swap` | 5 |
| `POST /api/v1/instructions` | 5 |

## Limits by plan

| Plan | Sustained | Burst | Keys | Stream connections |
|---|---|---|---|---|
| Free | 20 units/second | 40 units | 2 | — |
| Starter | 40 units/second | 80 units | 3 | 1 |
| Builder | 120 units/second | 240 units | 10 | 5 |
| Growth | 300 units/second | 600 units | 15 | 15 |
| Scale | 800 units/second | 1,600 units | 25 | 50 |
| Pro | 2,000 units/second | 4,000 units | 50 | 150 |
| Enterprise | Negotiated | Negotiated | Negotiated | Negotiated |

Through the cost table, a budget of N units/second is **N quotes/second, or N/5 transaction
builds/second, or any mix of the two** — Builder's 120 units is 120 quotes/second or 24 builds.

<Note>
**Limits are per account, not per key.** Creating more keys splits one integration's traffic
across them; it does not add budget. The same holds for stream connections: they are counted
across every key on the account.
</Note>

## Stream connections

`GET /api/v1/stream` is available from Starter up, capped at the plan's connection count across
the whole account. An upgrade on a plan without the stream returns `403` with code
`STREAM_NOT_IN_PLAN`; one past the limit returns `429` with code `STREAM_LIMIT`. A closed
connection frees its slot immediately.

<Info>
Free-plan keys keep **one** stream connection until **14 November 2026**, so integrations built
while the stream was free have time to move to a paid plan.
</Info>

## Anonymous access (no API key)

`GET /api/v1/quote`, `POST /api/v1/swap`, `POST /api/v1/instructions`, and `GET /api/v1/price`
all work with no `Authorization` header — useful for trying the API before you get a key.
Anonymous callers share a small per-IP bucket, debited by the same cost table:

| | Sustained | Burst |
|---|---|---|
| Anonymous (no key) | 2 units/second | 20 units |

A burst of 20 covers one `POST /api/v1/swap` (5 units) plus a handful of quotes. Anonymous access is for evaluation; for anything
else [get a key](/get-started/authentication) — same mechanics, at least 10× the budget, scoped to your
account rather than shared with every anonymous caller on your IP.

`GET /health` requires no key and is not subject to any of these limits.

### Per-IP ceiling (before authentication)

A second limiter runs **before** authentication and buckets by client IP rather than by key. It
protects the auth path from unauthenticated floods, so it applies to every `/api/v1/*` request —
including ones with a missing or invalid key — and to the WebSocket upgrade.

| | Sustained | Burst |
|---|---|---|
| Per client IP, pre-auth | 4,000 units/second | 8,000 units |

It sits at twice the highest plan's budget so it never binds on legitimate traffic from a
single customer; it should only trip on abuse. If you proxy many customers through one egress IP,
they share this ceiling even though their per-account budgets are separate.

<Note>
  The WebSocket handshake is covered by this per-IP limiter and by the plan's connection limit —
  the per-account request budget is not applied to the upgrade. Once connected, the stream is not
  rate limited per message.
</Note>

## Rate limit response

When rate limited, the API returns HTTP `429`:

```json
{
  "success": false,
  "error": "rate limit exceeded",
  "code": "RATE_LIMITED"
}
```

## Rate limit headers

Every rate-limited response, successful or not, reports where your bucket stands. Units are
**cost units**, not requests: a transaction build spends 5, a quote 1.

| Header | Meaning |
|---|---|
| `X-RateLimit-Limit` | Your bucket's capacity (the plan's burst) |
| `X-RateLimit-Remaining` | Cost units available right now, after this request |
| `X-RateLimit-Reset` | Seconds until the bucket is full again |
| `Retry-After` | On a `429` only: seconds until a request of this cost would be allowed |

The headers are exposed over CORS, so browser code can read them. Anonymous requests report
the anonymous bucket. The pre-auth per-IP ceiling sends only `Retry-After`.

## Retry strategy

On a `429`, wait `Retry-After` seconds if it is present. It is computed from your plan's
refill rate and the cost of the request you just made. Otherwise, use exponential backoff:

<CodeGroup>
```bash cURL
for i in 1 2 3; do
  response=$(curl -s -w "\n%{http_code}" "https://api.vulcx.xyz/api/v1/quote?inputMint=So11111111111111111111111111111111111111112&outputMint=uSd2czE61Evaf76RNbq4KPpXnkiL3irdzgLFUMe3NoG&amount=1000000000&swapMode=ExactIn")
  http_code=$(echo "$response" | tail -1)
  [ "$http_code" != "429" ] && echo "$response" && break
  sleep $((2 ** i))
done
```

```typescript TypeScript
async function fetchWithRetry(url: string, options?: RequestInit, maxRetries = 3) {
  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    const response = await fetch(url, options);

    if (response.status !== 429) return response;

    const delay = Math.pow(2, attempt) * 1000;
    await new Promise((r) => setTimeout(r, delay));
  }
  throw new Error("Rate limit exceeded after retries");
}
```

```python Python
import time
import requests

def fetch_with_retry(url, max_retries=3, **kwargs):
    for attempt in range(max_retries + 1):
        resp = requests.request(**kwargs, url=url)
        if resp.status_code != 429:
            return resp
        time.sleep(2 ** attempt)
    raise Exception("Rate limit exceeded after retries")
```
</CodeGroup>

## Best practices

- **Don't cache quotes.** A quote's firm commitment lives for `validForMs` (~3 s) and its
  price-or-fail window for `firmForMs` (~400 ms) — see [Firm quotes](/docs/swap/firm-quotes). Re-fetch
  before you build. (`lastValidBlockHeight` bounds how long the *transaction* can land, ~60 s; that
  is a different clock from how long the *price* is honoured.)
- **Stream instead of polling.** If your plan includes the stream and you need continuously fresh
  prices, subscribe on [`GET /api/v1/stream`](/api-reference/stream/index) — the connection is not
  per-message rate limited, so it is strictly cheaper than spending 1 unit per `/quote`.
- **Prefer `/instructions` over `/quote` + `/swap`.** One `POST /api/v1/instructions` costs 5 units;
  a `GET /api/v1/quote` followed by `POST /api/v1/swap` costs 6 and makes the engine route twice.
